# rlp-desk 7차 요청 — codex "usage limit reset available" 배너의 제출 차단: 즉시-재주입 필요 (P2) — 2026-07-21

요청자: tire-plletdata PO 세션. v0.22.15 재개 캠페인(pa-foundation)에서 **같은 배너로 인한 미제출 2회 재현** — 사용자가 직접 목격하고 "몇 번이고 요청했다"고 지적한 그 증상의 잔여분이다. 2차 요청 ③(제출 보장)의 커버리지 갭.

## 증상 (2회 재현, 동일 패턴)

- codex pane(verifier leg)에 트리거 프롬프트가 **입력창에 에코된 채 미제출 대기**. pane 상단에 배너:
  ```
  • You have 1 usage limit reset available. Run /usage to use one.
  ```
  (참고: "increased plan usage" 문구도 동반 관측)
- 이 배너는 소진(exhausted)이 아니라 **"리셋 소비 가능" 상태** — 2차 요청 ③의 배너-내성이 다룬 "resets available" 계열이지만, 제출 자체가 막히는 케이스가 실존한다.
- 1회차: 사용자가 직접 목격(수동 Enter로 해소, 주입 6초 만에 정상 실행). 2회차: 우리측 임시 워치독(20초 주기)이 감지·주입(주입 9초 만에 정상 실행). **두 번 모두 Enter 1회로 즉시 해소** — 즉 순수 제출-지연이며 작업·계정 문제 아님.

## 관측 한계 (정직 고지)

- 현행 기본 SUBMISSION_TIMEOUT=90s의 자동 재주입이 이 케이스를 결국 잡는지는 **미관측** — 1회차는 사용자가, 2회차는 우리 20초 워치독이 선점했다. 잡는다 해도 **디스패치마다 최대 90초의 상시 지연**이 발생하는 구조다 (캠페인당 디스패치 수십 회 = 누적 수십 분).

## 요청

1. **알려진-배너 즉시 재주입**: 트리거 send-keys 직후(2~5초) pane 스냅샷에서 ①프롬프트 에코 존재 + ②진행 신호 부재 + ③알려진 배너 패턴(`usage limit reset available`, `increased plan usage`, weekly-limit 계열) 감지 시 **90초를 기다리지 말고 즉시 Enter 1회 재주입**. (2차 요청서 ③에서 "제출 확인 주기는 짧게 2~3s 권장"이라 적었던 부분의 실구현 — 현재는 첫 체크가 90s.)
2. 배너 패턴 목록은 설정 가능(env 또는 파일)하게 — codex CLI 버전마다 문구가 바뀐다.
3. 재주입 후에도 미실행이면 기존 90s 경로로 자연 합류 (변경 없음).

## 수용 기준

- 위 배너 상태에서 미제출 idle이 ≤10초 내 자동 해소 (실측 2회 케이스 기준).
- 정상 즉시-제출 케이스에 재주입 0 (진행 신호 감지 시 skip — 기존 원칙).

## 우리측 임시 조치 (배포 전까지)

- 세션 워치독(20초 주기, 전 pane: 에코+무진행 → Enter) 운영 중 — 배포되면 제거한다. 이런 로컬 워치독이 다시 필요해졌다는 사실 자체가 이 요청의 근거다.
