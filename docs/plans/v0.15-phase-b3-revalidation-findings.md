## §2 — Why bands were tightened (not loosened) despite negative drift

The synthetic baseline was a **conservative ceiling** — derived as the zsh-leader's 5s POLL_INTERVAL upper bound. Reality (Node leader, 100ms poll) is much faster. Tightening the bands to ~3× empirical p95 catches real regressions earlier without producing false positives in normal runs.

### §2.1 — Multiplier raised from 2× to 3× (deviation from plan v3 AC3.5 formula)

Plan v3 §B3 AC3.5 prescribes `band = max(p95 × 2, fixed_floor)`. Revalidation findings used **3× p95** instead because:

1. The harness has **no LLM** in the worker/verifier panes — they're plain shells that exit on the first `C-c`. Real-LLM scenarios (claude/codex TUI doing self-review post-write) have higher tail latency, especially for pane_eof_to_cleanup_ms (TUI cleanup path) and pane_reap_latency_ms (done-claim observe + reap).
2. N is small (5-10 samples). 3× cushions against tail behavior the small sample can't capture.
3. Stage 2 is non-blocking by default; tighter bands produce more INFO warnings, which are useful signal-of-change without breaking the gate. When `B3_STAGE2_BLOCKING=1` is set (post-revalidation by user nightly), the 3× cushion remains conservative.

This deviation is documented inline in `tests/sv-real-llm/lib/b3-lifecycle-assertions.sh` and recorded here so a future maintainer can revisit if the LLM-jitter assumption proves incorrect.

### §2.2 — `pane_eof_to_cleanup_ms` keeps 5000ms despite empirical 834ms

`killPaneProcess` worst-case is `gracePeriodMs=800ms + exitTimeoutMs=5000ms = 5800ms`. The band must envelope this even if every observed run is <1s — otherwise a single legitimate worst-case teardown would mark a regression. 5000ms is the production-correct ceiling regardless of what the harness samples.
